## Additional movement defect found and fixed

A repeated local native comparison exposed random demolition respawns: independently allocated cores selected opposite legal spawn sides. The recovered RocketSim `Car::Respawn` uses a random selection when invoked with seed -1. The current native checkpoint does not serialize that random generator. Therefore a client must not reveal an independently predicted spawn before the server confirms its lifecycle.

`src/online/presentation-lifecycle.js` keeps a confirmed demolished local car and its camera target at the server's last pose, then reveals the confirmed respawn without carrying an ordinary motion-correction offset across that discontinuity. Ordinary predicted driving remains unchanged. Nearby-ball presentation does not blend toward a demolished car's speculative contact state. A dedicated test crosses an actual native respawn and deliberately confirms the other legal spawn side. Reordered player slots and immutability of authoritative state are tested.

This is a presentation/lifecycle fix, not serialization of RNG or Bullet solver caches. Speculative simulation and later authoritative corrections still exist. It does not guarantee that every collision or packet-loss condition is invisible.

The old native bit-equality fixture mixed algorithm comparison with random respawns. It now uses identical nonintersecting jump/boost lanes, asserts that no demolition occurs, and retains strict per-tick equality for 1,000 ticks with 2/4/6 cars. Collision/aerial tests remain in the suite, and the new native respawn regression explicitly tests the previously uncontrolled case. No equality tolerance was loosened to conceal random divergence.

## Research applied

- [Riot, VALORANT Gameplay Consistency Update, 2022-04-15](https://playvalorant.com/en-us/news/game-updates/valorant-gameplay-consistency-update/): input bursts, latency variation and alt-tab frame throttling can cause unstable buffering even when average ping is modest. This supports keeping frame, network and server timing distinct, not simply increasing tick rate.
- [Rocket League v1.58, 2019-02-19](https://www.rocketleague.com/news/patch-notes-v1-58): documented STS/CSTS input timing feedback. The existing bounded clock feedback is an independent implementation, not exact current Rocket League code.
- [Glenn Fiedler, State Synchronization](https://gafferongames.com/post/state_synchronization/): physics authority and visible smoothing are separate responsibilities; approximation and packet gaps remain limits. Lifecycle teleports need explicit handling, not indefinite smoothing of a wrong pose.
- [Epic, Networked Physics Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networked-physics-overview): resimulation requires historical physics state and has processing/memory costs. The previously integrated native checkpoint addresses exposed gameplay fields but not every engine internal.
- [MDN, WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket): the API has no automatic backpressure. Existing bounded histories, stale snapshot handling and congestion recovery matter; WebSocket/TCP is not turned into an unreliable datagram transport by these changes.
- [Render free-service documentation](https://render.com/docs/free): free services can sleep and take about a minute to start; free instances are not a production reliability guarantee. The bounded acceptance retry is not an artificial keep-alive service or a fix for provider CPU limits.
